# Задача для обучения: планировщик спринтовых задач

> Это пример задачи, не более того — под конкретный воркшоп задача может быть другой.

## Проблема

Сейчас планирование спринта идёт так: команда обсуждает вслух (Miro/встреча), кто-то
записывает всё в Word-файл, файл рассылается, и потом задачи вручную заводятся в корпоративном
трекере — это медленно, трекер тяжёлый и заводить в нём напрямую неудобно.

## Продукт (MVP)

Веб-UI, где Product Owner:
- видит список эпиков (эпик = сервис или цель — единица группировки задач),
- пишет задачу текстом, опционально привязывает её к эпику из выпадающего списка (или
  оставляет без привязки — тогда это "общая" задача),
- указывает одного или нескольких исполнителей.

Если исполнителей несколько — задача размножается: заводится отдельная запись на каждого
исполнителя, а не одна задача "на двоих".

Результат MVP — сформированный и провалидированный командой общий список задач. Автозаведение
в корпоративный трекер через его API — следующий этап, вне рамок текущего MVP.

## Данные (общие для всех команд, не зависят от стека)

- **Эпик** — имя.
- **Задача** — текст, ссылка на эпик (опционально), список исполнителей (минимум один).
- Хранение — только в памяти процесса, без БД. Данные сбрасываются при перезапуске — для MVP
  это осознанно допустимо.

## Стеки по командам

| Команда | Backend | Рендеринг | Хранение |
|---|---|---|---|
| Python | FastAPI + Uvicorn | Jinja2 (server-side, обычные HTML-формы) | в памяти |
| JavaScript | Express | server-side шаблоны (EJS/Pug), обычные HTML-формы | в памяти |
| Java | Spring Boot (Spring Web) | Thymeleaf | в памяти |

Каждая команда работает только в своём языке: рендеринг везде серверный, без отдельного
JS-фреймворка на фронте — иначе Python- и Java-командам пришлось бы дополнительно писать ещё и
JS, что ломает принцип "один язык на команду".
