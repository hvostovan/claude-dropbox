# План Team Leader — техническая подготовка и ведение обучения

> Отдельно от `team-training-plan.md` (тот — про роли и общий процесс). Это — конкретно твой
> операционный план: что настраиваешь, что запускаешь, какими командами. Часть пунктов ждёт
> задачу (пока плейсхолдеры) — обновим, как только пришлёшь.

## Роль в двух словах

Готовишь инфраструктуру и рамку (архитектурные ограничения), ведёшь процесс, следишь, что
каждый передаёт следующей роли письменный артефакт, а не пересказ на словах. Задачи за роли не
решаешь.

## До Дня 1: что настроить

1. Создать репозиторий для командного упражнения (отдельный от `claude-dropbox` — это боевой
   репо команды на время обучения).
2. Базовая разметка и установка:
   ```
   mkdir <project> && cd <project>
   npm init -y
   npm install <зависимости под задачу>
   openspec init
   mv .qwen .gigacode   # в меню выбрать Qwen (пробел), затем Enter
   ```
3. Скачать и распаковать `openspec-context-pack-template.zip`, доложить `openspec/context/` и
   `config.yaml` поверх того, что создал `openspec init` (не заменять сам `openspec init`).
4. Заполнить минимальный набор контекст-файлов самому, до начала Дня 1 (решили: без `05`):
   - `00-start-here.md` — короткий указатель на остальные файлы контекста, не больше экрана
   - `03-architecture.md` — архитектурные инварианты и ограничения — **[ЖДЁМ ЗАДАЧУ]**
   - `04-engineering-standards.md` — 3-5 правил по стилю/стеку — **[ЖДЁМ ЗАДАЧУ]**

   Остальные файлы пака (`01`, `02`, `05`, `06`, `07`, `ADR/`, `examples/`, `failure-log.md`) —
   не создаём: их по смыслу формируют роли в ходе самого упражнения (PO — продуктовый контекст,
   аналитик — глоссарий/спеку, QA — критерии тестирования), готовить их заранее значило бы
   отобрать у ролей их часть работы.
5. Проверить `openspec/config.yaml` — в блоке `context:` должны быть перечислены реально
   созданные файлы (`00-start-here.md`, `03-architecture.md`, `04-engineering-standards.md`),
   иначе GigaCode их не подхватит.
6. Прогнать самому `gigacode` один раз и спросить агента что-то вроде "что ты знаешь про
   архитектуру проекта" — должен процитировать содержимое `03-architecture.md`. Это проверка,
   что контекст реально читается, а не просто лежит в папке.
7. Убедиться, что у каждого участника поднято рабочее окружение (Node.js, npm, GigaCode CLI,
   доступ к репозиторию).

## Шпаргалка команд

| Шаг | Команда |
|---|---|
| Создать проект | `mkdir <project> && cd <project>` |
| Инициализировать npm | `npm init -y` |
| Поставить зависимости | `npm install <...>` |
| Инициализировать OpenSpec | `openspec init` |
| Переключить на GigaCode | `mv .qwen .gigacode` (в меню выбрать Qwen) |
| Запустить GigaCode | `gigacode` |
| Обсудить требования | `/opsx-explore "..."` |
| Создать спецификацию | `/opsx-propose "..."` |
| Сгенерить/изменить код по спеке | `/opsx-apply` |
| Закрыть задачу | `/opsx-archive` |

## В процессе (День 1 / День 2) — что делаешь руками

- Держишь шпаргалку под рукой, чтобы подсказывать команды, если кто-то завис.
- На стыках ролей проверяешь, что артефакт реально записан в файл (не осталась в устной
  форме) — см. чек-поинты в `team-training-plan.md`.
- Если участник не может продвинуться — не решаешь за него, а задаёшь наводящий вопрос по
  SDD-цепочке ("а что из этого попало в спеку?").
