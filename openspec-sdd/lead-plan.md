# План Team Leader — техническая подготовка и ведение обучения

> Отдельно от `team-training-plan.md` (тот — про роли и общий процесс). Это — конкретно твой
> операционный план: что настраиваешь, что запускаешь, какими командами. Содержимое
> контекст-файлов ниже — реальные шаблоны из материала Сбербанка, подрезанные под наш
> минимальный набор. Раз используем только `start-here` + `architecture` +
> `engineering-standards` (без `product-context/domain-glossary/security-and-compliance/
> testing-and-quality/anti-patterns` — решили их не создавать, роли сформируют свою часть в
> ходе упражнения), пронумеровали подряд без дырок: `00-start-here.md`, `01-architecture.md`,
> `02-engineering-standards.md`. Плейсхолдеры в `[квадратных скобках]` — ждут задачу, впишу
> конкретику как только пришлёшь.

## Роль в двух словах

Готовишь инфраструктуру и рамку (архитектурные ограничения), ведёшь процесс, следишь, что
каждый передаёт следующей роли письменный артефакт, а не пересказ на словах. Задачи за роли не
решаешь.

## До Дня 1: пошагово

**1. Создать репозиторий** для командного упражнения (отдельный от `claude-dropbox` — это
боевой репо команды на время обучения).

**2. Установка проекта** (пример для Node.js — под свой стек в другой ветке команда адаптирует
инициализацию под себя, например `python -m venv .venv` вместо `npm init`):
```
mkdir <project> && cd <project>
npm init -y
openspec init
mv .qwen .gigacode   # в меню выбрать Qwen (пробел), затем Enter
```
Зависимости (`npm install ...` / `pip install ...` и т.п.) ставим не сейчас вслепую, а по ходу
разработки — когда станет понятно, что именно нужно под задачу.

**3. Создать папку контекста и три файла вручную** (без скачивания архива):
```
mkdir -p openspec/context
```
Дальше создать три файла — содержимое см. ниже.

**4. Заменить `openspec/config.yaml`** на версию ниже — там список файлов подрезан под наш набор.

**5. Заполнить плейсхолдеры** `[в квадратных скобках]` реальным содержанием — как только пришлёшь
задачу, впишу конкретику вместо плейсхолдеров сам.

**6. Проверить, что контекст читается:** прогнать `gigacode` один раз, спросить агента что-то
вроде "что ты знаешь про архитектуру проекта" — должен процитировать `01-architecture.md`.

**7. Проверить окружение** (Node.js, npm, GigaCode CLI, доступ к репозиторию).

## Содержимое файлов

### `openspec/context/00-start-here.md`
```markdown
---
owner: Тимлид (context owner)
updated: [ГГГГ-ММ-ДД]
---
# Start Here
> Только навигация и главные запреты, не само знание. Держать на один экран.

Работаешь с продуктом: [название].

## Перед началом любой задачи
1. Прочитай 01-architecture.md.
2. Прочитай 02-engineering-standards.md.
3. Не делай изменений вне scope задачи.
4. Не хватает контекста — сформулируй, какого, и не угадывай.

## Главные запреты
- [запрет 1]
- [запрет 2]
```

### `openspec/context/01-architecture.md`
```markdown
---
owner: Архитектор / Тимлид

---
# Architecture
> 3-5 инвариантов + ссылка на актуальную схему. Историю эволюции — в ADR (не заводим),
> тяжёлые диаграммы — ссылкой.

## Инварианты
1. [архитектурное правило, которое нельзя нарушать]

## Обязательные / запрещённые паттерны
- Обязательно: [паттерн] для [случай].
- Запрещено: [паттерн], потому что [причина].

## Схема
Актуальная схема: [ссылка], обновлена [дата].

## Ключевые интеграции и зависимости
[upstream/downstream системы, API]
```

### `openspec/config.yaml`
```yaml
# openspec/config.yaml
# Связка контекста с OpenSpec: context инжектится во ВСЕ артефакты,
# rules — только в свой артефакт.

schema: spec-driven

context:
  Продукт: [Название]. [1-2 предложения, что это].
  Стек: [...].

Если описание в _raw расходится с актуальным кодом — верь коду, спорное выноси человеку.

Перед созданием ЛЮБОГО артефакта обязательно прочитай файлы из openspec/context/:
- 00-start-here.md, 01-architecture.md, 02-engineering-standards.md
Не хватает контекста — НЕ угадывай, сформулируй, какого, и не молчи.

rules:
  proposal:
    - Всегда заполняй Scope и Non-goals.
    - Противоречие требований — подними вопрос человеку.
  specs:
    - Если описание в _raw расходится с кодом — верь коду.
  design:
    - Опирайся на инварианты из 01-architecture.md.
  tasks:
    - Не делай refactor вне задачи.
```

## Шпаргалка команд

| Шаг | Команда |
|---|---|
| Создать проект | `mkdir <project> && cd <project>` |
| Инициализировать npm | `npm init -y` |
| Поставить зависимости | `npm install <...>` |
| Инициализировать OpenSpec | `openspec init` |
| Переключить на GigaCode | `mv .qwen .gigacode` (в меню выбрать Qwen) |
| Запустить GigaCode | `gigacode` |
| Обсудить требования | `/opsx-explore "..."` |
| Создать спецификацию | `/opsx-propose "..."` |
| Сгенерить/изменить код по спеке | `/opsx-apply` |
| Закрыть задачу | `/opsx-archive` |

## В процессе (День 1 / День 2) — что делаешь руками

- Держишь шпаргалку под рукой, чтобы подсказывать команды, если кто-то завис.
- На стыках ролей проверяешь, что артефакт реально записан в файл (не осталась в устной
  форме) — см. чек-поинты в `team-training-plan.md`.
- Если участник не может продвинуться — не решаешь за него, а задаёшь наводящий вопрос по
  SDD-цепочке ("а что из этого попало в спеку?").
