# Плейбуки по ролям

Порядок = порядок цепочки. Каждый читает результат предыдущего, не спрашивает "на словах".
Валидация (Этап 3) — прямое ревью командой, без git/PR.

| Этап | Роль | Команда | Делаешь | Выход |
|---|---|---|---|---|
| 1. Intent | Product Owner | `/opsx-intent` (без аргумента) | Отвечаешь на вопросы агента своими словами | `openspec/changes/<id>/intent.md` |
| 2. Спецификация | Системный аналитик | `/opsx-propose @openspec/changes/<id>/intent.md` | Отвечаешь на уточняющие вопросы, опираясь на `01-architecture.md` | Спецификация в change |
| 3. Валидация | Вся команда | — | Читаете спеку вместе, согласуете или правите | Утверждённая спека |
| 4. Разработка | Разработчик | `/opsx-apply` | Сверяешься с `02-engineering-standards.md`, при неясности — назад к спеке, не гадаешь | Код |
| 5. Тестирование | QA | нет спец-команды — запуск приложения + `/opsx-archive` в конце | Прогон руками через UI по сценариям, отчёт | `openspec/changes/<id>/test-report.md` |

**Правило Этапа 3:** разработчик не начинает `/opsx-apply`, пока команда явно не согласилась,
что спека готова.

**Этап 5 подробнее:** запусти приложение (команда — из `02-engineering-standards.md` своей
ветки), пройди сценарии руками через браузер:
```
- Given два исполнителя, When PO создаёт задачу на обоих, Then две отдельные записи.
- Given нет эпиков, When задача создаётся без эпика, Then задача общая, без ошибки.
- Given перезапуск сервера, When открываешь список, Then данные пустые — это ожидаемо (in-memory).
```
Расхождения — не правишь сам, возвращаешь разработчику. Нужны автотесты, а не только руки —
попроси агента обычным текстом ("напиши тесты на pytest/jest/JUnit под эти сценарии"), спец-
команды для этого нет. В конце — `/opsx-archive`.

**Lead:** не работает за роли, следит, что каждый этап заканчивается файлом, а не словами.
Отдельно — что ревью на Этапе 3 настоящее, а не формальное.
