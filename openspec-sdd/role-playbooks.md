# Плейбуки по ролям — для сольного прогона

> Инструкция для тебя, чтобы пройти все 4 роли самостоятельно один раз до самого обучения:
> примерить шапку каждой, увидеть, где может застрять участник, и обкатать промпты. Задача и
> инварианты — см. `task.md` и `teams/<стек>/openspec/context/01-architecture.md`. Перед стартом
> у тебя уже должен быть создан проект и `openspec/context/` из `lead-plan.md` +
> `teams/<свой стек>/`.

Порядок ролей = порядок цепочки артефактов: PO → Системный аналитик → Разработчик → QA. Каждая
роль читает результат предыдущей, а не спрашивает "на словах".

---

## 1. Product Owner

**Вход:** идея (уже есть, см. `task.md`).
**Выход:** сформулированный бизнес-запрос — не финальная спека, а свободный текст с целью,
проблемой и границами, который дальше уточняется вместе с агентом.

**Что делаешь:** запускаешь `/opsx-explore` и своими словами (не обязательно копировать
дословно) объясняешь, что нужно. Пример промпта:

```
/opsx-explore "Хочу веб-приложение — планировщик спринтовых задач. Сейчас на планировании всё
проговариваем вслух, записываем в Word, потом руками заводим в корпоративный трекер — это
медленно. Нужно, чтобы Product Owner мог: видеть список эпиков (эпик — это сервис или цель),
писать задачу текстом, опционально привязывать её к эпику из выпадающего списка, указывать
одного или нескольких исполнителей. Если исполнителей несколько — по каждому нужна отдельная
запись задачи. Результат — общий список задач, который команда потом вместе проверяет.
Заводить задачи в реальный трекер пока не нужно — это следующий этап."
```

Агент задаст уточняющие вопросы (что не входит в MVP, нужна ли авторизация, нужно ли хранить
данные между перезапусками и т.п.) — отвечай как PO, ориентируясь на инварианты из
`01-architecture.md` (без БД, без интеграции с трекером, без авторизации).

**Когда закончил:** требования проговорены и понятны — переходишь к аналитику. Если с самого
начала всё ясно (для рехёрсла — почти наверняка так, задача уже согласована), `/opsx-explore`
можно пропустить и сразу перейти к `/opsx-propose`.

---

## 2. Системный аналитик

**Вход:** результат `/opsx-explore` (или сразу задача от PO, если explore пропустили).
**Выход:** формальная спецификация (OpenSpec сам создаст артефакты — спеку, дизайн, список
задач; точные имена файлов увидишь после команды).

**Что делаешь:** запускаешь `/opsx-propose` с формализованным описанием — данные, сценарии,
границы. Пример промпта:

```
/opsx-propose "Создать MVP планировщика спринтовых задач.
Данные: Эпик {название}. Задача {текст, ссылка на эпик — опционально, список исполнителей,
минимум один}.
Сценарии:
- PO создаёт эпик.
- PO создаёт задачу с одним исполнителем → появляется одна запись.
- PO создаёт задачу с несколькими исполнителями → появляется отдельная запись на каждого.
- PO создаёт задачу без эпика → задача создаётся как общая, без привязки.
- Список задач отображается сгруппированным по эпикам, плюс отдельно общие задачи.
Хранение — только в памяти процесса, без БД. Рендеринг — server-side, без отдельного
JS-фреймворка на фронте, без AJAX (обычные HTML-формы).
Не входит в MVP: авторизация, интеграция с трекером, персистентное хранилище."
```

**После генерации:** обязательно прочитай, что агент создал (спеку/дизайн/список задач) — как
аналитик, проверь, что сценарии покрывают граничные случаи (задача без эпика, несколько
исполнителей), а не только счастливый путь. Если чего-то не хватает — дозаполни руками или
попроси агента уточнить конкретный раздел, не весь `/opsx-propose` заново.

**Когда закончил:** спека отражает реальные требования — переходишь к разработке.

---

## 3. Разработчик

**Вход:** готовая спецификация от аналитика.
**Выход:** рабочий код.

**Что делаешь:**
```
/opsx-apply
```
Агент пошагово генерирует/меняет файлы проекта по спеке. По ходу:
- сверяйся с `02-engineering-standards.md` своей ветки (какой стек, какие команды тестов/линта);
- если агент на чём-то застрял или спека неоднозначна — не додумывай сам, вернись к спеке или
  задай уточняющий вопрос в сессии;
- прогони тесты/линт из шпаргалки `lead-plan.md`.

**Когда закончил:** приложение запускается, реализует сценарии из спеки — переходишь к QA.

---

## 4. QA / Тестировщик

**Вход:** спецификация + работающий код.
**Выход:** отчёт о тестировании (что проверено, что не сходится со спекой).

**Что делаешь:** пишешь тест-кейсы по спеке, в стиле Given/When/Then, отдельное внимание —
граничным случаям, а не только счастливому пути:

```
- Given список исполнителей из двух человек, When PO создаёт задачу с обоими, Then появляются
  две отдельные записи задачи (по одной на каждого).
- Given пустой список эпиков, When PO создаёт задачу без выбора эпика, Then задача создаётся
  как общая, без привязки, и не падает с ошибкой.
- Given задача создана без эпика, When список задач отображается, Then она видна в разделе
  "общие", а не теряется.
```

Прогоняешь руками через UI (приложение простое — server-rendered формы, тестировать можно
кликами, без отдельных тестовых фреймворков). Расхождения со спекой — фиксируешь и возвращаешь
разработчику, а не молча правишь сам.

**Когда закончил:** сценарии из спеки подтверждены — можно `/opsx-archive`.

---

## Итог

После прохождения всех четырёх ролей самостоятельно у тебя будет: (1) чёткое понимание, где
именно участники могут застрять на реальном обучении, (2) обкатанные примеры промптов, которые
можно давать командам как подсказку, если кто-то не знает, с чего начать.
