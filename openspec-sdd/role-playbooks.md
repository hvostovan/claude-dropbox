# Плейбуки по ролям — по официальному процессу SDD (Сбербанк, TO BE)

> 5 шагов из официальной схемы: Идея/Intent → Спецификация (PR) → Валидация спецификации
> (ревью + merge PR = утверждение) → Разработка → Тестирование. Ключевое отличие от того, что
> было в черновике раньше: спецификация проходит через **Pull Request с ревью и мерджем до
> начала разработки** — это отдельный шаг с отдельным артефактом (утверждённая спека), а не
> просто "аналитик написал — разработчик сразу начал".

Порядок = порядок цепочки. Каждая роль читает результат предыдущей, не спрашивает "на словах".

---

## Этап 1 — Идея / Intent (Product Owner)

**Вход:** ничего, начало цикла.
**Выход:** Intent — короткий письменный текст: что меняем и зачем.

**Что делаешь:** пишешь текстом (диалог с AI не обязателен — задача уже понятна). Пример
содержания уже есть в общей идее из презентации: планировщик спринтовых задач, проблема с
Word-файлом и медленным трекером, кто получает пользу.

> Если хочешь потренировать более формальную фасилитацию Intent — в материалах Сбербанка есть
> skill `sber-intent` (структурированный диалог с классификацией типа Intent). Для этого
> упражнения — необязательно, обычного текста достаточно, задача не расплывчатая.

**Когда закончил:** Intent сформулирован — передаёшь аналитику.

---

## Этап 2 — Формирование спецификации (Системный аналитик)

**Вход:** Intent от PO.
**Выход:** Спецификация / артефакт SDD — **оформленная как Pull Request**, ещё не утверждённая.

**Что делаешь:**
1. Создаёшь ветку под изменение: `git checkout -b spec/task-planner`
2. Запускаешь агента с промптом (данные, сценарии, границы — под нашу задачу):
```
/opsx-propose "Создать MVP планировщика спринтовых задач.
Данные: Эпик {название}. Задача {текст, ссылка на эпик — опционально, список исполнителей,
минимум один}.
Сценарии:
- PO создаёт эпик.
- PO создаёт задачу с одним исполнителем → появляется одна запись.
- PO создаёт задачу с несколькими исполнителями → появляется отдельная запись на каждого.
- PO создаёт задачу без эпика → задача создаётся как общая, без привязки.
- Список задач отображается сгруппированным по эпикам, плюс отдельно общие задачи.
Хранение — только в памяти процесса, без БД. Рендеринг — server-side, без отдельного
JS-фреймворка на фронте, без AJAX.
Не входит в MVP: авторизация, интеграция с трекером, персистентное хранилище."
```
3. Проверяешь сгенерированные артефакты — покрыты ли граничные случаи, а не только счастливый
   путь.
4. Коммитишь, пушишь ветку, **открываешь Pull Request**.

**Когда закончил:** PR открыт — передаёшь на валидацию команде.

---

## Этап 3 — Валидация спецификации (вся команда, до начала разработки)

**Вход:** открытый PR со спецификацией.
**Выход:** утверждённая спецификация — **смердженный PR**.

**Что делают все:** читают PR, оставляют комментарии — противоречия, пробелы, вопросы. Если
что-то не так — аналитик правит спеку в той же ветке (не начинается заново).

**Ключевое правило:** **разработчик не начинает `/opsx-apply`, пока PR не смерджен.** Merge —
это формальный акт утверждения, не техническая формальность. Пока не смерджено — считается, что
спецификации ещё нет.

**Роль лида здесь:** следит, чтобы ревью реально происходило (не формальный "апрув не глядя"), и
либо сам жмёт Merge, либо назначает, кто это делает.

**Когда закончили:** PR смерджен — передаёте разработчику.

---

## Этап 4 — Разработка (Разработчик)

**Вход:** утверждённая (смердженная) спецификация.
**Выход:** исходный код.

**Что делаешь:**
```
/opsx-apply
```
Агент пошагово генерирует/меняет файлы проекта по спеке. По ходу:
- сверяйся с `02-engineering-standards.md` своей ветки (стек, команды тестов/линта);
- если что-то в спеке неоднозначно — не додумывай сам, возвращайся к спеке, а не гадай;
- Code Review — кто-то из команды смотрит diff перед тем, как считать этап законченным.

**Когда закончил:** приложение реализует сценарии из спеки — передаёшь QA.

---

## Этап 5 — Тестирование (QA)

**Вход:** спецификация + работающий код.
**Выход:** тестовые сценарии + отчёт о тестировании.

**Что делаешь:** пишешь тест-кейсы по спеке в стиле Given/When/Then, с упором на граничные
случаи, не только счастливый путь:

```
- Given список исполнителей из двух человек, When PO создаёт задачу с обоими, Then появляются
  две отдельные записи задачи (по одной на каждого).
- Given пустой список эпиков, When PO создаёт задачу без выбора эпика, Then задача создаётся
  как общая, без привязки, и не падает с ошибкой.
- Given задача создана без эпика, When список задач отображается, Then она видна в разделе
  "общие", а не теряется.
```

Прогоняешь руками через UI (приложение простое, server-rendered — тестировать можно кликами).
Расхождения со спекой — фиксируешь и возвращаешь разработчику, не молча правишь сам.

**Когда закончил:** сценарии из спеки подтверждены — цикл завершён, можно `/opsx-archive`.

---

## Роль Lead на всех этапах

Не выполняет работу за роли, а следит, что каждый этап реально заканчивается письменным
артефактом (Intent → PR со спекой → смердженный PR → код → тестовый отчёт), а не устной
договорённостью. Отдельно владеет Этапом 3 — следит, чтобы ревью PR было настоящим, не формальным.
