# Плейбуки по ролям — по официальному процессу SDD (Сбербанк, TO BE)

> 5 шагов из официальной схемы: Идея/Intent → Спецификация → Валидация спецификации (ревью
> командой до начала разработки) → Разработка → Тестирование. Pull request/git-ветки в рамках
> этого обучения не используем — валидация происходит прямым ревью сгенерированной спеки
> командой, без git-механики.

Порядок = порядок цепочки. Каждая роль читает результат предыдущей, не спрашивает "на словах".

---

## Этап 1 — Идея / Intent (Product Owner)

**Вход:** ничего, начало цикла.
**Выход:** артефакт **intent.md** — что меняем, почему сейчас, что должно получиться, как
измеряем успех.

**Что делаешь:** запускаешь `/opsx-intent` (это тот же skill `openspec-intent`, известный также
как `sber-intent`, из материалов Сбербанка — подрезанный под наше упражнение: без рамки
"ежедневная утренняя сессия", с явным требованием сохранить результат файлом, версия в
`skills/sber-intent-trimmed.md`) **без аргумента**:

```
/opsx-intent
```

Агент сам задаст первый вопрос ("Какое изменение или улучшение вы хотите создать?") и дальше
поведёт сократический диалог (не чек-лист) — отвечай как PO своими словами, в диалоге, а не
заготовленным заранее текстом: идея (планировщик спринтовых задач), проблема (Word → медленный
трекер), кто получает пользу — раскрываешь по ходу разговора, отвечая на уточняющие вопросы.

Когда ясность достигнута, агент обязан физически создать файл
`openspec/changes/<change-id>/intent.md` (не просто вывести текст в чат — это проверено вживую:
первая версия skill без явной инструкции про запись файла остановилась на тексте в чате).

**Когда закончил:** файл `intent.md` реально лежит в `openspec/changes/<change-id>/` —
передаёшь аналитику.

---

## Этап 2 — Формирование спецификации (Системный аналитик)

**Вход:** `openspec/changes/<change-id>/intent.md` от PO.
**Выход:** Спецификация / артефакт SDD (файлы, которые создаёт OpenSpec), ещё не утверждённая.

**Что делаешь:**
1. Запускаешь агента **без аргумента**:
```
/opsx-propose
```
2. Агент спросит, что строить. В ответе набираешь `@` — GigaCode сам ищет и предлагает файлы
   по мере ввода — находишь и выбираешь `intent.md` из `openspec/changes/<change-id>/` (тот,
   что создал PO на Этапе 1). Никакого текста от себя заранее готовить не нужно — только
   прикрепить файл.
3. Дальше агент задаёт уточняющие вопросы — отвечаешь как аналитик, своими словами, в диалоге,
   опираясь на `01-architecture.md` (инварианты: без БД, размножение задачи по исполнителям,
   server-side рендеринг без JS-фреймворка) и здравый смысл, а не по заготовленному сценарию.
4. Проверяешь сгенерированные артефакты — покрыты ли граничные случаи, а не только счастливый
   путь.

**Когда закончил:** спецификация готова — передаёшь на валидацию команде.

---

## Этап 3 — Валидация спецификации (вся команда, до начала разработки)

**Вход:** готовая спецификация от аналитика.
**Выход:** утверждённая командой спецификация.

**Что делают все:** читают спецификацию вместе, оставляют замечания — противоречия, пробелы,
вопросы. Если что-то не так — аналитик правит спеку на месте (не начинается заново).

**Ключевое правило:** **разработчик не начинает `/opsx-apply`, пока команда явно не согласилась,
что спека готова.** Пока нет согласия — считается, что спецификации ещё нет.

**Роль лида здесь:** следит, чтобы ревью реально происходило (не формальное "и так сойдёт"), и
фиксирует момент, когда команда согласилась, что спека готова.

**Когда закончили:** спецификация утверждена — передаёте разработчику.

---

## Этап 4 — Разработка (Разработчик)

**Вход:** утверждённая (смердженная) спецификация.
**Выход:** исходный код.

**Что делаешь:**
```
/opsx-apply
```
Агент пошагово генерирует/меняет файлы проекта по спеке. По ходу:
- сверяйся с `02-engineering-standards.md` своей ветки (стек, команды тестов/линта);
- если что-то в спеке неоднозначно — не додумывай сам, возвращайся к спеке, а не гадай;
- Code Review — кто-то из команды смотрит diff перед тем, как считать этап законченным.

**Когда закончил:** приложение реализует сценарии из спеки — передаёшь QA.

---

## Этап 5 — Тестирование (QA)

**Вход:** спецификация + работающий код.
**Выход:** тестовые сценарии + отчёт о тестировании.

**Что делаешь:** пишешь тест-кейсы по спеке в стиле Given/When/Then, с упором на граничные
случаи, не только счастливый путь:

```
- Given список исполнителей из двух человек, When PO создаёт задачу с обоими, Then появляются
  две отдельные записи задачи (по одной на каждого).
- Given пустой список эпиков, When PO создаёт задачу без выбора эпика, Then задача создаётся
  как общая, без привязки, и не падает с ошибкой.
- Given задача создана без эпика, When список задач отображается, Then она видна в разделе
  "общие", а не теряется.
```

Прогоняешь руками через UI (приложение простое, server-rendered — тестировать можно кликами).
Расхождения со спекой — фиксируешь и возвращаешь разработчику, не молча правишь сам.

**Когда закончил:** сценарии из спеки подтверждены — цикл завершён, можно `/opsx-archive`.

---

## Роль Lead на всех этапах

Не выполняет работу за роли, а следит, что каждый этап реально заканчивается письменным
артефактом (Intent → спека → утверждённая спека → код → тестовый отчёт), а не устной
договорённостью. Отдельно владеет Этапом 3 — следит, чтобы ревью спеки было настоящим, не
формальным.
