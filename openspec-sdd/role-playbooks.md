# Плейбуки по ролям

Порядок = порядок цепочки. Каждый читает результат предыдущего, не спрашивает "на словах".
Валидация (Этап 3) — прямое ревью командой, без git/PR.

## 1. Intent — Product Owner

Запускаешь без аргумента, дальше диалог своими словами:
```
/opsx-intent
```
Агент должен физически создать `openspec/changes/<id>/intent.md` — не просто ответить в чате
(проверено вживую: без явного требования он останавливается на тексте в чате).

**Выход:** `intent.md`.

## 2. Спецификация — Системный аналитик

```
/opsx-propose @openspec/changes/<id>/intent.md
```
Отвечаешь на уточняющие вопросы своими словами, опираясь на `01-architecture.md`.

**Выход:** спецификация в change.

### Доработка спеки (если QA нашёл пробел — Этап 5, Тип Б)
```
@openspec/changes/<id>/spec.md обнаружен пробел: [конкретный кейс] не описан. Предлагаю: [...].
Обнови спеку.
```
Команда коротко соглашается с обновлением (мини-версия Этапа 3, не обязательно заново
формально всё).

## 3. Валидация — вся команда

Читаете спеку вместе, оставляете замечания, аналитик правит на месте.

**Правило:** разработчик не начинает `/opsx-apply`, пока команда явно не согласилась, что спека
готова.

**Выход:** утверждённая спека.

## 4. Разработка — Разработчик

```
/opsx-apply
```
Сверяешься с `02-engineering-standards.md` своей ветки. Неясность в спеке — возвращаешься к
ней, не гадаешь.

**Выход:** код.

### Доработка (если QA нашёл проблему — Этап 5)
Баг реализации, спека верна, код не соответствует (Тип А):
```
@openspec/changes/<id>/spec.md по спеке должно быть [...], а по факту [...]. Почини.
```
После того как аналитик закрыл пробел в спеке (Тип Б):
```
@openspec/changes/<id>/spec.md спека обновилась в части [...] — реализуй это.
```
Тест написан неправильно (не соответствует `test-cases.md`):
```
Тест [X] не соответствует test-cases.md, там должно быть [...]. Поправь тест.
```

## 5. Тестирование — QA

> 📄 **Все подробности и готовые промпты — в отдельном файле `qa-testing-guide.md`.**

Спец-команды нет, обычный диалог с агентом. Сначала руками через браузер (смок-тест), потом
тест-кейсы (`test-cases.md`, сам правишь), потом агент пишет и сам гоняет автотесты. Проблемы
делятся на баг реализации / пробел в спецификации — чинятся по-разному.

**Выход:** `test-cases.md` (провалидирован QA) + тестовый код + зелёный прогон.

## Lead

Не работает за роли. Следит, что каждый этап заканчивается файлом, а не словами. Отдельно — что
ревью на Этапе 3 настоящее, не формальное.
