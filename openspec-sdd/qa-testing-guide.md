# Этап 5 (Тестирование) — подробности для QA

Дополнение к `role-playbooks.md`. Спец-команды нет — обычный диалог с агентом. Файл появится,
только если явно попросить сохранить его — иначе, скорее всего, останется текстом в чате (та же
особенность, что и на Этапе 1). Шаги ниже — план, **не проверено вживую**, прогони и поправь
под факт.

## Шаг 0 — сначала руками, до тест-кейсов и автотестов

Запускаешь приложение (команда — из `02-engineering-standards.md` своей ветки) и вручную
проходишь по сценариям спеки через браузер — быстрый смок-тест.

**Нашёл проблему — сначала определи тип, это разные пути починки:**

**Тип А — баг реализации** (в спеке написано верно, по факту не так). QA сверяется со спекой,
отдаёт ноутбук разработчику, показывает конкретно: что делал → что должно быть по спеке → что
получил по факту. Разработчик правит точечно, не обязательно весь `/opsx-apply` заново:
```
@openspec/changes/<id>/spec.md по спеке должно быть [...], а по факту [...]. Почини.
```

**Тип Б — пробел в спецификации** (в спеке про этот кейс не написано или написано
неоднозначно). Это не баг кода — нельзя чинить, пока не решено, как должно быть. Сначала
обновляется спека:
```
@openspec/changes/<id>/spec.md обнаружен пробел: [конкретный кейс] не описан. Предлагаю: [...].
Обнови спеку.
```
Команда коротко соглашается с обновлением (мини-версия Этапа 3, не обязательно заново
формально всё). Только после этого разработчик реализует именно изменившуюся часть:
```
@openspec/changes/<id>/spec.md спека обновилась в части [...] — реализуй это.
```

В обоих случаях: разработчик отдаёт ноутбук обратно, QA перепроверяет именно тот сценарий, что
был проблемным (не всё заново). Только когда ручная проверка вся чистая — переходишь к шагам
ниже.

## Шаги 1–5 — когда ручная проверка чистая

1. Сформировать тест-кейсы по спеке:
```
@openspec/changes/<id>/spec.md сформируй тест-кейсы (Given/When/Then, текстом) и сохрани в
файл test-cases.md рядом со спекой
```
2. Сам читаешь и правишь `test-cases.md` — свежий взгляд "как это сломать", не то же самое, что
   сценарии аналитика.
3. Сгенерировать и запустить автотесты по провалидированному списку:
```
На основе test-cases.md напиши и запусти автотесты на [pytest/jest/JUnit]
```
Агент создаёт тестовый файл в коде и сам его запускает (shell-доступ), результат — в терминале.

4. Красный вывод — сначала пойми, что сломано: тест или код.
   - **Тест написан неправильно** (не соответствует провалидированному `test-cases.md` —
     агент напутал при переводе в код). Чинишь тест, не код:
     ```
     Тест [X] не соответствует test-cases.md, там должно быть [...]. Поправь тест.
     ```
   - **Тест написан правильно, а код не проходит** — та же развилка, что в Шаге 0: баг
     реализации (Тип А) или пробел в спецификации (Тип Б), см. выше, те же промпты.

   В обоих случаях правит разработчик тем же ноутбуком, потом QA просит:
```
Запусти тесты снова
```
5. Всё зелёное:
```
/opsx-archive
```

**Выход:** `test-cases.md` (провалидирован QA) + тестовый код + зелёный прогон.
