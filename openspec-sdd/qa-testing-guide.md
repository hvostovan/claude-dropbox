# Этап 5 (Тестирование) — подробности для QA

Дополнение к `role-playbooks.md`. Спец-команды нет — обычный диалог с агентом. Файл появится,
только если явно попросить сохранить его — иначе, скорее всего, останется текстом в чате (та же
особенность, что и на Этапе 1). Шаги ниже — план, **не проверено вживую**, прогони и поправь
под факт.

## Шаг 0 — сначала руками, до тест-кейсов и автотестов

Запускаешь приложение (команда — из `02-engineering-standards.md` своей ветки) и вручную
проходишь по сценариям спеки через браузер — быстрый смок-тест.

**Нашёл проблему — определи тип, дальше чинить будет не QA:**

**Тип А — баг реализации** (в спеке написано верно, по факту не так). Сверяешься со спекой,
отдаёшь ноутбук разработчику, показываешь конкретно: что делал → что должно быть по спеке → что
получил по факту. Сам промпт и доработка — у разработчика, `role-playbooks.md`, Этап 4.

**Тип Б — пробел в спецификации** (в спеке про этот кейс не написано или написано
неоднозначно). Не твоя работа чинить код, пока не решено, как должно быть. Отдаёшь ноутбук
аналитику, описываешь конкретный кейс. Промпт — у аналитика, `role-playbooks.md`, Этап 2. После
того как спека обновится и команда коротко согласится — разработчик реализует изменившуюся
часть (тоже Этап 4).

В обоих случаях: тебе отдают ноутбук обратно, перепроверяешь именно тот сценарий, что был
проблемным (не всё заново). Только когда ручная проверка вся чистая — переходишь к шагам ниже.

## Шаги 1–5 — когда ручная проверка чистая

1. Сформировать тест-кейсы по спеке:
```
@openspec/changes/<id>/spec.md сформируй тест-кейсы (Given/When/Then, текстом) и сохрани в
файл test-cases.md рядом со спекой
```
2. Сам читаешь и правишь `test-cases.md` — свежий взгляд "как это сломать", не то же самое, что
   сценарии аналитика.
3. Сгенерировать и запустить автотесты по провалидированному списку:
```
На основе test-cases.md напиши и запусти автотесты на [pytest/jest/JUnit]
```
Агент создаёт тестовый файл в коде и сам его запускает (shell-доступ), результат — в терминале.

4. Красный вывод — пойми, что сломано: тест или код (тест — Тип А/Б, применяются так же, как в
   Шаге 0). Чинит разработчик (и аналитик для пробела в спеке) — промпты у них,
   `role-playbooks.md`. Ты только просишь:
```
Запусти тесты снова
```
5. Всё зелёное:
```
/opsx-archive
```

**Выход:** `test-cases.md` (провалидирован QA) + тестовый код + зелёный прогон.
